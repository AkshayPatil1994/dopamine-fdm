# Examples

← [[Home|Home]]

Several runnable cases live under `examples/`, each a self-contained `input_parameters`
(and, for the IBM case, a geometry). Copy a case's directory contents next to the
`dopamine` executable (or point `filein`/paths at it), create the output directories
(see [[Installation § Running|Installation#running]]), and launch with `mpirun`.

## `les_chan395`

A canonical **wall-resolved LES channel flow** at $Re_\tau \approx 395$.

- `nx,ny,nz = 66,65,66`, `Lx,Ly,Lz = 6.0,2.0,2.0`, `grid_type = 2` (symmetric tanh)
- `nu = 1/395`, `dPdx = 1.0` — non-dimensionalised so $u_\tau = 1$, $H = 1$
- `sgs_model = 1` (Vreman LES)
- `ic_type = 5` (inverse-linear profile to accelerate transition — see
  [[Numerics § Initial conditions|Numerics#12-initial-conditions]])
- Fixed `dt = 1.0`, `nsteps = 120000`
- Periodic in $x$ and $z$ (`x_bc_type = 0`, default)

This is the reference case to validate a fresh build against — compare resulting
mean-velocity and Reynolds-stress profiles against Moser–Kim–Mansour DNS data (see
`postProcessing/analyse_channel.py` in
[[Pre- and Post-Processing Tools|Tools#analyse_channelpy]]).

## `dns_ibm_wavyWall`

A **DNS over a rough (wavy) wall** using the ghost-cell IBM, reproducing ERCOFTAC Classic
Collection Case 076 "Flow over a wavy wall" (Buckles, Hanratty & Adrian, *J. Fluid Mech.*
1984; $Re_H = U_b H/\nu = 6760$).

- `nx,ny,nz = 258,129,130`, `Lx,Ly,Lz = 4.0,1.05,2.0`, `grid_type = 6` (roughness
  sublayer + tanh)
- `sgs_model = 0` (DNS), `x_bc_type = 0` (periodic), `ibm_input_mode = 1` (SDF-based
  ghost-cell IBM, reading the precomputed cell-centre SDF `ibm_sdf_file = 'SDF_in'`)
- `nsteps = -10` — negative, so the run is driven by `sim_end_time` rather than a fixed
  step count (see [[Numerics § Stopping criteria|Numerics#33-stopping-and-save-interval-criteria]])

The bottom-wall geometry is generated by `geo/generate_wavy_wall.py`, which builds a
closed, watertight STL for the sinusoidal wall:

$$\frac{y - y_0}{a} = \cos\\!\left(\frac{2\pi x}{\lambda} + \text{phase}\right), \qquad \frac{2a}{\lambda} = 0.10$$

(height-to-wavelength ratio per the Case 076 spec). Feed the resulting STL to `GenSDF`
(`geo/parameters.in` is a ready-made `GenSDF` config for this geometry) to produce the
`SDF_in` the solver reads — see
[[Pre- and Post-Processing Tools § GenSDF|Tools#gensdf]].

For validation results (mean velocity and Reynolds stress profiles against DNS) from
this exact case, see
[[Numerics § IBM Validation|Numerics#63-validation--turbulent-flow-over-a-wavy-wall]].

## `precursor_successor`

Demonstrates **precursor–successor coupling**: a periodic "precursor" simulation
generates fully-developed turbulence, whose planes are recycled as a time-resolved
inflow for a downstream "successor" simulation with an inflow/outflow streamwise BC.
Both cases share the same domain size (`nx,ny,nz = 130,65,66`, `Lx,Ly,Lz = 12.0,2.0,6.0`,
`grid_type = 2`) and LES setup (`sgs_model = 1`).

- **`precursor/`** — a standard periodic channel (`x_bc_type = 0`, `dPdx = 1.0`,
  `ic_type = 1`), run with `nsteps = -200` (i.e. to `sim_end_time`) while writing plane
  slices to `slices/precursor*` for the successor to consume.
- **`successor/`** — `x_bc_type = 1` (inflow/outflow), `dPdx = 0.0` (no imposed mean
  gradient — the inflow carries the momentum), and `inflow_recycle_file =
  '../precursor/slices/precursor'` with `inflow_recycle_loop = 1` to replay the
  precursor's recorded planes as a time-resolved inlet condition. `ic_type = 1` is set
  but not used for initialisation in this mode.

> This recycling inflow mode (`inflow_type`, `inflow_recycle_file`,
> `inflow_recycle_loop`) is broader than the constant/SEM options documented in
> [[Input Parameters § INFLOW|Input-Parameters#inflow-optional--used-only-when-x_bc_type--1]];
> consult `src/` (`sem.f90` / `boundary_conditions.f90`) or open an issue if the recycle
> workflow needs deeper docs.

**Running order**: run `precursor/` to completion first (so `slices/precursor*` exists
and has enough recorded planes), then run `successor/` from its own directory, pointing
`inflow_recycle_file` at the precursor's output.

## UAV actuator disk (`examples/uav_*`)

Six small, quick-running cases exercising the `&UAV` actuator-disk rotor model (see
[[Input Parameters § &UAV|Input-Parameters#uav-optional--omit-to-disable]] for every
parameter). All six use a
small `nx,ny,nz = 66,(65 or 129),66`, `Lx,Ly,Lz = 1.0,(1.0 or 2.0),1.0` box, `sgs_model = 0`
(DNS), and a hover thrust `uav_hover_thrust = 4.0` (kinematic thrust for a ~0.5 kg UAV at
`rho_air ~ 1.2 kg/m^3`).

- **`uav_hover_disk`** — a static disk at box centre in an otherwise quiescent, free-slip
  domain (no ground): the baseline hover check.
- **`uav_ground_effect/{near_ground,far_ground}`** — a static disk over the domain's own
  no-slip ground at `h/R = 2` and `h/R = 8` respectively (`ny = 129`, `Ly = 2.0`); compare
  induced velocity just below the disk between the two with
  `uav_ground_effect/analyze_ground_effect.py` to see the reduced-induced-velocity
  ground-effect trend.
- **`uav_path_takeoff`** — a single-rank vertical climb following `uav_takeoff_path.dat`
  (`uav_path_active = 1`), from near the ground up to altitude, in quiescent air.
- **`uav_path_cross_rank`** — the same idea but horizontal, with `p_row = 2` (2 MPI ranks
  splitting $x$) so the path in `uav_cross_path.dat` carries the disk's kernel support
  straight through the rank boundary; run with `mpirun -np 2`. This is the one case that
  exercises `apply_uav_forcing`'s per-rank partial-cell force projection.
- **`uav_wind_takeoff`** — `uav_path_takeoff`'s climb repeated under a steady mean
  crosswind (`flow_forcing_mode = 1` constant-mass-flux forcing, `Ub_target = 3.0`) over
  the rough-free log-law ground, following `uav_wind_path.dat`.
- **`uav_tilt_translate`** — a takeoff → horizontal translate → land path
  (`uav_tilt_path.dat`) that actually exercises `uav_tilt_active = 1` (unlike
  `uav_path_takeoff`'s pure vertical climb, where the auto-tilt would stay at
  `(0,1,0)` throughout even if enabled), together with `uav_load_profile = 1`
  (parabolic tip-tapered loading) and `uav_swirl_frac = 0.05` (torque-reaction
  swirl), on a `66x129x66` LES grid (`sgs_model = 1`). Confirms the combination is
  stable (divergence stays at the same ~1e-12 level as the other UAV cases) and
  that the tilt genuinely injects horizontal momentum: bulk `<U>` peaks around
  `-0.26` during the translate/deceleration-into-landing phase, versus staying at
  the noise floor (`~1e-3`) for the whole run with `uav_tilt_active = 0,
  uav_swirl_frac = 0.0` as a control.

`postProcessing/generate_UAVpath.py` renders any of these cases' path file as a
moving-disk ParaView animation (see
[[Pre- and Post-Processing Tools § generate_UAVpath.py|Tools#generate_uavpathpy]]).
